   173→PreOne Prisma Schema v3.0 | Database Implementation Freeze
   174→1. Introduction
   175→Document Purpose
   176→This Prisma Schema v3.0 document is the authoritative reference for the complete
   177→database implementation of the PreOne Enterprise Preschool Operating System. It
   178→consolidates 288 Prisma models, 84 enum definitions, 412 foreign key relations, full index
   179→and constraint specifications, 15 migration scripts, comprehensive seed data, and CI/CD
   180→pipeline configuration into a single Database Implementation Freeze. Every NestJS service,
   181→every Prisma Client call, and every database migration in the PreOne platform must
   182→conform to this document.
   183→This document supersedes the schema snippets scattered across DDD v1.0 and ERD v3.0.
   184→Where those documents describe the domain model and entity relationships conceptually,
   185→this document specifies the concrete Prisma schema that engineers will implement. It
   186→includes the model definitions, the field types, the relation annotations, the index
   187→declarations, the constraint definitions, the migration scripts, and the seed data. Engineers
   188→should treat this document as the source of truth for any database-related question.
   189→Scope & Applicability
   190→The document covers the entire PostgreSQL-backed data layer for PreOne across all 15
   191→domain bounded contexts: Identity, Marketing & CRM, Admissions, Student, Academics,
   192→Daily Operations, Communication, Finance, Inventory, HR, Administration, Reports,
   193→Settings, Platform, and Common. It governs schema design, relation cardinalities, multi-
   194→tenant isolation, audit columns, soft-delete semantics, indexing strategy, enum taxonomy,
   195→migration lifecycle, seed data, performance tuning, and naming conventions. Any engineer,
   196→contractor, or AI agent touching the prisma/ directory must read this document first.
   197→The document applies to all PreOne environments: local development, staging, production,
   198→and the ephemeral preview environments spun up for each pull request. It applies to the
   199→primary PostgreSQL database; it does NOT apply to Redis (cache), Elasticsearch (search
   200→indexing), or S3 (file storage) — those have their own schemas documented separately. Any
   201→data that needs to be queried relationally, transactionally, or with multi-tenant isolation
   202→lives in PostgreSQL and follows this schema.

   296→2. Prisma Standards
   297→ORM Selection & Version
   298→PreOne uses Prisma ORM v5+ as the exclusive database access layer. Direct SQL access via
   299→pg, knex, or raw queries is FORBIDDEN in application code; the only exception is migration
   300→scripts that need database features Prisma cannot express (e.g., GIN index creation, full-
   301→text search triggers). Prisma was chosen over TypeORM and MikroORM because of its
   302→generated type-safe client, declarative schema syntax, first-class migration tooling, and
   303→excellent PostgreSQL feature coverage.
   304→Prisma was selected after a six-week evaluation period during which the team prototyped
   305→the same Student-management module in Prisma, TypeORM, MikroORM, and Kysely.
   306→Prisma won on three dimensions: (a) the generated TypeScript client eliminated an entire
   307→class of runtime errors that TypeORM's decorator-based approach allowed, (b) the
   308→migration tooling produced reviewable SQL that DBAs could sign off on, and (c) the
   309→declarative schema syntax was readable enough for product managers to review during
   310→sprint planning.
   311→Version: Prisma CLI and @prisma/client are pinned to ^5.18.0 in package.json. Minor
   312→version upgrades require running the full migration suite against a shadow database in CI
   313→and verifying zero diff. Major version upgrades (v6, v7) require an Architecture Decision
   314→Record and a coordinated migration plan; they are not permitted in patch releases.. The CLI,
   315→the client, and all @prisma/* packages must be on the same minor version. The engine
   316→binary is auto-downloaded by the postinstall script and pinned via the binaryTargets field in
   317→generator.prisma.
   318→ORM Rules
   319→The six rules below are non-negotiable. They are enforced by code review, by lint rules
   320→(eslint-plugin-prisma), and by Prisma middleware that fails fast on violations. An engineer
   321→who breaks these rules in a PR will be asked to refactor before the PR can merge.

   325→Rule Detail
   326→Use Prisma Client everywhere All database reads and writes go through the
   327→generated Prisma Client. No raw queries in
   328→services, no repositories that wrap pg,
   329→noKnex usage. Prisma's type safety is the
   330→contract between the database and the
   331→application.
   332→Use Prisma migrations for schema changes Never run prisma db push against any
   333→environment above local dev. All schema
   334→changes go through prisma migrate dev
   335→(local) and prisma migrate deploy
   336→(CI/staging/prod). Migrations are immutable
   337→once merged.
   338→Use transactions for multi-table writes Any operation that writes to two or more
   339→tables must use prisma.$transaction(). Never
   340→write multiple tables in sequence without a
   341→transaction; partial writes corrupt data.
   342→Use Prisma's typed include/select Always specify which relations to load via
   343→include or select. Never fetch entire rows
   344→with all relations (N+1 problem). Use Prisma's
   345→type inference to ensure compile-time safety
   346→of relation loading.
   347→Use Prisma middleware for cross-cutting Tenant isolation, soft-delete filtering, and
   348→concerns audit logging are implemented as Prisma
   349→middleware/extensions. Engineers must not
   350→duplicate these concerns in service code.
   351→Use Prisma's schema preview features prismaSchemaFolder is enabled for multi-file
   352→judiciously schema. MultiSchema is NOT enabled (single
   353→schema). FullTextIndex is enabled for
   354→PostgreSQL GIN indexes. PostgresExtensions
   355→is enabled for uuid-ossp and pg_trgm.

   403→3. Folder Structure
   404→Multi-File Schema Overview
   405→PreOne's prisma/ directory uses the prismaSchemaFolder preview feature to split the
   406→schema across multiple .prisma files organized by domain. Each domain owns its own folder
   407→with one or more .prisma files. The main schema.prisma file contains only the datasource,
   408→generator, and preview feature declarations. This structure mirrors the DDD bounded
   409→contexts and keeps each domain's schema self-contained for easier review and merge
   410→conflict resolution.
   411→The prismaSchemaFolder preview feature is enabled in generator.prisma. This feature
   412→allows the schema to be split across multiple .prisma files, each in its own domain folder.
   413→Prisma merges these files at generation time into a single logical schema. This structure
   414→mirrors the DDD bounded contexts and makes schema review easier — a PR touching only
   415→the Finance domain only needs to touch prisma/finance/, and reviewers can focus on that
   416→folder.

   493→4. Schema Architecture
   494→Architecture Overview
   495→PreOne's schema architecture is a single-schema PostgreSQL design with multi-tenant
   496→isolation enforced at the application layer via Prisma middleware. We do NOT use schema-
   497→per-tenant or database-per-tenant isolation because (a) the multi-tenant filter is enforced
   498→programmatically in every query, (b) tenant-aware RLS (Row-Level Security) is enabled as a
   499→defense-in-depth measure, and (c) the operational cost of per-tenant schemas at 1000+
   500→schools would be prohibitive. Every business table contains tenantId, branchId, and
   501→academicYearId columns (where applicable) to enable the cascade filter.
   502→The shared-database pattern was chosen after evaluating three alternatives: schema-per-
   503→tenant (operational complexity at 1000+ schemas), database-per-tenant (cost-prohibitive
   504→at 1000+ databases), and PostgreSQL RLS-only (too easy to bypass with a missed policy).
   505→The shared-database pattern with application-layer enforcement plus RLS as defense-in-
   506→depth provides the best balance of cost, complexity, and safety. The Prisma middleware is
   507→the primary enforcement; if a developer forgets to filter by tenantId, the middleware
   508→throws and the request fails.
   509→Schema Layers
   510→The schema is organized into five horizontal layers. Each layer has a clear responsibility and

   542→Multi-Tenant Strategy
   543→Pattern Shared database, shared schema, tenant-
   544→discriminator column
   545→Discriminator tenantId (UUID, indexed, non-null on all
   546→business tables)
   547→Enforcement Prisma middleware (primary), PostgreSQL RLS
   548→(defense-in-depth)
   549→Cascade tenantId is required on insert. Updates to
   550→tenantId are FORBIDDEN (immutable). Branch
   551→changes within a tenant are permitted only
   552→by Admin role.
   553→Isolation Each query must filter by tenantId. The
   554→Prisma middleware automatically injects
   555→tenantId from the request context. Direct
   556→prisma.client calls without tenantId in WHERE
   557→clause are blocked by middleware and fail at
   558→runtime.
   559→Audit Columns
   560→Every   model   inherits   from   a   Base   mixin   that   adds   these   7   columns.   The
   561→createdBy/updatedBy/deletedBy columns store the user ID (UUID) of the actor. The version
   562→column is an integer that increments on every update (optimistic concurrency control).
   563→Soft-delete semantics: deletedAt is nullable. Soft-deleted records have deletedAt != null.
   564→Prisma middleware filters out soft-deleted records by default. Hard deletes are FORBIDDEN
   565→except for: audit cleanup jobs (records > 7 years old), temporary OTP codes (TTL 10 min),
   566→and session cache (TTL 24 h).

   570→The seven required audit columns are: createdAt, createdBy, updatedAt, updatedBy,
   571→deletedAt, deletedBy, version. The version column enables optimistic concurrency control:
   572→when an update is issued, Prisma middleware automatically adds a WHERE version =
   573→current_version clause and increments the version. If the row was modified by another
   574→transaction, the update matches zero rows and the service throws a ConcurrencyError.
